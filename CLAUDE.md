# Kanjiru

A daily kanji puzzle in the spirit of Wordle: guess the kanji (or a 2–4 kanji word) from its parts. Each guess colours its parts: right part in the right spot, right part in the wrong spot, or not in the answer.

## Start here
- **`docs/DESIGN.md`**: every game decision so far, marked Decided, Proposed or Open, with the reasons. Confirm anything Proposed with the user before building on it.
- **`docs/ROADMAP.md`**: the steps to launch, their order, and the prompt that starts each one. Tick a step off when it merges, and update both docs when a decision changes.
- **Threads share this folder.** Two sessions here at once will switch each other's Git branches, so run one at a time or give each its own worktree.

## Tech Stack
- **Frontend:** vanilla JS (ES modules), no build step. `tokens.js` is a classic script loaded in `<head>`; everything else is a module from `app.js`.
- **Backend:** PHP, only for small endpoints (`api/transfer.php`, the device-transfer code). The game itself runs in the browser. The site runs PHP 8.2; write for 7.4 and up.
- **Data:** generated by a Python script (`tools/build_data.py`, stdlib only) from KANJIDIC2, KanjiVG, JMdict and Jonathan Waller's JLPT lists. Credits in `data/ATTRIBUTION.md`.
- **Hosting:** Bluehost (shared PHP hosting), at https://www.ryanrwang.com/apps/kanjiru/

## Word data
- Rebuild: `python -I tools/build_data.py` from this folder. Sources are pinned; downloads go to `tools/sources/` (ignored by Git).
- Review: open `http://localhost:8095/apps/kanjiru/review/` with the PHP server running.
- Waller's kanji lists come from Internet Archive snapshots, because tanos.co.uk is offline.
- Known part-breakdown problems to solve before the game uses them: loose strokes that aren't components (本, 未 and 末 all become 木), contents of an enclosure marked `none` instead of `inner` (国, 間), positions relative to a subgroup (命), variant forms (氵 vs 水, `orig`), unprintable `CDP-…` component names (原, 願, 武, 源), and atomic answers (金, 車, 雨).

## Rules
- **Everything is a catalogue.** Modes, skins, powers, achievements and point values live in `js/config/`. Code reads them through `js/registry.js` and never hard-codes a list, a length, a price or an id. Growing the game means adding entries.
- **No text in code or catalogues.** Every word the player sees comes from `t('key')` in `js/i18n.js`, with the text in `js/i18n/en.js` and `js/i18n/ja.js`. Catalogue text is keyed by id (`mode.k1.name`, `skin.theme.ai`, `power.sweep.desc`, `achievement.streak-7.name`). A new catalogue entry needs its text in every language; `validate()` warns when any is missing. A new language is a new file plus an entry in `LANGUAGES`.
- **Language:** `settings.lang` in the save (null = follow the device). It sets `<html lang>`. Kanji meant to look like kanji get `lang="ja"` or `.kanji` for the serif; plain Japanese UI text stays in the sans font. Dictionary meanings are English only for now.
- **Powers are data, effects are code.** A power names an `effect` the engine implements once. A new power that reuses an effect with new `params` needs no code. A new effect goes in `KNOWN_EFFECTS` in `js/registry.js` and in the engine.
- **Ids are permanent.** Saves store mode, skin, power and achievement ids. Never rename one; add a new entry and retire the old.
- **The save is versioned.** Changing its shape means bumping `VERSION` in `js/store.js` and adding a migration. Adding a key needs nothing: missing keys are filled from `fresh()`.
- **History is the source of truth.** Streaks and stats are worked out from `history`, never stored as counters.
- **Check the console.** `validate()` logs `[kanjiru config]` warnings at start-up when catalogues disagree. Fix them before committing.
- **Answers are N3 or easier.** Guesses may use any jōyō kanji built from the puzzle's palette.
- **Game data is compiled.** After a rebuild or a review session, run `python -I -X utf8 tools/compile_game.py` and commit `data/game/`. It never invents answers: with no Keep words the answer lists are empty.
- **Testing the game before words are reviewed:** put a few answers in a local `data/game/answers.json` and run `git update-index --skip-worktree data/game/answers.json` so they can't be committed. Undo with `--no-skip-worktree` and `git checkout data/game/answers.json`. Never commit made-up answers.
- **Which modes play:** a mode needs `playable: true` in `js/config/modes.js` (the game screen supports it) and answers. Until both, the start screen shows "soon".
- **Dev-only files don't deploy.** `tools/`, `review/`, `tests/`, `package.json`, `data/candidates.json` and `data/review.json` are excluded in `deploy.yml`. The review page writes files, so it must never reach the server.
- **Server data stays put.** `api/transfer.php` writes codes to `api/codes/`, which is gitignored, blocked by `.htaccess` and excluded in `deploy.yml`.
- **Back-to-apps mark:** this app's hover move is `rw-brush`, a left-to-right clip-path wipe. Keep it unique across the apps family.

## Design Tokens

The project uses a centralized design token system defined in `tokens.js` with light/dark theme support.

`tokens.js` exposes two interfaces:
- **`window.TOKENS`**: `primitives`, `semantic` (base light), `themes`, and `resolve(themeId, scheme)`, `applyLook(themeId, scheme)`, `active()`
- **CSS custom properties**: injected on `:root`, `[data-scheme="dark"]` and one block per skin, `[data-theme="<id>"]` and `[data-theme="<id>"][data-scheme="dark"]`

### Skins
- `<html data-theme>` picks the skin, `<html data-scheme>` picks light or dark within it.
- A skin lists only the semantic tokens it changes. A plain colour skin is one line: `name: accentTheme(c.palette)`, given a palette with the stops 50, 100, 300, 500, 700, 800, 900, 950.
- A skin may have one scheme only (`urushi` is dark-only); the scheme toggle is then disabled.
- Adding a skin: palette in `primitives.color`, colours in `THEMES`, catalogue entry in `js/config/skins.js` with the same id.

### Rules
- **All code must use tokens** for colors, spacing, sizing, typography, border-radius, shadows, opacity, and transitions. Never hardcode these values.
- **Use semantic tokens first** (`var(--color-text-primary)` or `TOKENS.active().color.text.primary`). Fall back to primitives only when no semantic token exists.
- **Before adding any new design value**, check `tokens.js` first. If the value exists, use it. If not, add a new primitive and semantic token before using it.
- **All spacing and sizing must use the 4px base grid:** 1, 2, 4, 8, 12, 16, 20, 24, 32, 40, 48, 56, 64, 80, 96, 128. Off-grid values are not allowed.
- **Breakpoints and z-index are intentionally NOT tokenized.** They have implicit ordering dependencies. Do not refactor without explicit approval.
- **Feedback colours are tokens too** (`--color-feedback-hit/near/miss`), so a skin, or a colour-blind mode later, can change them.

### Usage — CSS
```css
.my-element {
  color: var(--color-text-secondary);
  background: var(--color-bg-surface);
  padding: var(--spacing-md);
  border-radius: var(--radius-sm);
}
```

### Usage — JavaScript
```javascript
var t = window.TOKENS.active();
element.style.color = t.color.text.secondary;
```

## Repo Hygiene

### After push or PR
- Run `git status`, `git stash list`, `git branch -a`, and `git fetch --prune` to verify clean state.
- Flag any stale branches, uncommitted changes, or divergence.
- Ask the user what they'd like to work on next.

## "Push to prod"

When the user says **"push to prod"**, execute this full pipeline automatically:

1. **Commit** any uncommitted changes on the current branch (if any)
2. **Push** the branch to GitHub (`git push -u origin <branch>`)
3. **Create a PR** via `gh pr create`
4. **Merge the PR** immediately via `gh pr merge --squash` — use squash merge so the merge commit title on `main` is the descriptive PR title
5. **Switch to main** and pull (`git checkout main && git pull`)
6. **Delete the feature branch** locally (`git branch -d <branch>`)
7. **Prune** stale remote refs (`git fetch --prune`)
8. Run the standard post-push hygiene checks (status, stash list, branch -a)

If already on `main` with uncommitted changes, commit and push directly — no PR needed.
